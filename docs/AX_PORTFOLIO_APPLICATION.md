# FabGuard: 문제와 검증을 보여주는 포트폴리오

## 적용 범위

2026-09-17 사용자 제공 AX 포트폴리오 교육자료의 독자 관점, 근거 연결,
사람과 AI의 역할 구분 원칙을 FabGuard 소개 화면에 적용했다.
자료의 가상 사례·수치·채용 관련 주장은 프로젝트 성과의 근거로 사용하지 않았다.
원본 교재, 슬라이드 이미지, 예시 코드는 재배포하지 않는다.

이번 변경은 소개 화면과 그 근거 문서를 연결하는 하나의 작업이다.
새 학습, 데이터 추가, 평가 변경, 프레임워크·런타임 의존성 추가는 없다.

## 이 프로젝트에서 보여줄 판단

| 항목 | FabGuard에서의 선택 |
|---|---|
| 주요 독자 | 반도체 공정·품질·스마트제조 직무 검토자 |
| 전달할 역량 | 제한된 점검 여력을 문제로 정의하고, AI 위험순위의 유용성과 한계를 검증하는 과정 |
| 핵심 질문 | 어떤 생산 건부터 확인하며, 그 범위에서 무엇을 놓치는가? |
| 결과의 근거 | V1 결과 CSV와 실험계약, 테스트 노출 기록 |
| 확인 방식 | 실행 가능한 점검 목록, 원자료 링크, 역할 및 한계 설명 |
| 사람의 역할 | 저장소 기여 기록에 명시된 문제·범위 결정, 결과 검토, 공개·병합 판단 |
| AI의 역할 | 실험·평가 코드, 화면·문서·테스트 작성 보조 및 실제 변경 구현 |
| 아직 증명하지 못한 것 | 독립 제조 데이터 성능, 현장 수율·비용 개선, 실제 공정 원인 |

## 화면 변경

- 첫 소개 영역에 포착 수, 분모, 범위 밖 불량 수와 잠정 판정 이유를 함께 배치.
- 중복된 소개·건수 요약을 줄이고 결과 다음에 세 종류의 증거를 배치.
- 상세 제작 과정은 펼쳐 읽도록 하여 초기 정보량을 제한.
- `#process`로 제작 판단과 검증 근거에 직접 진입 가능.
- 모든 새 결과 건수는 기존 `web/data/summary.json`에서 계산한다.
- 잘못된 건수·분모 또는 잠정 상태 누락 시 검증 없이 결과를 표시하지 않는다.
- 원자료와 모델 파이프라인은 그대로 유지한다.

## 결과에서 검토 요청까지

추가 수업의 `결과 → 근거 → 계산 검증 → 연락` 구조를 다음처럼 적용했다.

1. **결과**: 상위 40건에서 불량 5건을 포착했다는 잠정 결과를 먼저 제시한다.
2. **원자료**: 전체 392건·불량 24건·누락 19건·정상 점검 35건과 Top-K CSV를 연결한다.
3. **계산 검증**: `(5/40)/(24/392) = 2.04`를 화면에 표시하고, JSON의 lift가 이 계산과 다르면 렌더링을 중단한다.
4. **검토 요청**: 저장소 이슈로 재현 불일치·누락된 한계·표시 오류를 제보할 수 있게 한다.

수업 예시의 `적용 전후` 형식은 채택하지 않았다. FabGuard에는 실제 공정 개입 전후를
비교한 증거가 없기 때문이다. 2.04배는 점검 범위의 불량 집중도이며 개선율, 인과효과,
비용 절감 또는 수율 향상을 뜻하지 않는다.

## 추가 취업 특강 자료의 적용

사용자가 제공한 다음 세 자료에서 직무에 맞는 경험 선택, 구체적인 행동 설명,
근거에 기반한 AI 초안 작성 원칙을 참고했다. 아래 내용은 FabGuard의 기존 기록을
재구성한 것이며, 강사의 평가나 외부 전문가의 프로젝트 검증을 뜻하지 않는다.

| 제공 자료 | 참고한 부분 | 적용 |
|---|---|---|
| [털보아저씨] 한국공학대학교 전자, 반도체 전공자 취업 특강 강의자료_학생 공유용 | 직무별 업무·역량, 직무와 경험의 연결, 문제 확인 후 검증하는 사례 | 직무별 증거와 미입증 범위를 짝지음 |
| 숭실대학교_생성형 AI를 활용한 입사지원서 준비 전략_유재천 | 자기 분석 → 상대 분석 → 작성, STAR에서 행동의 이유와 방법 강조 | 사람과 AI의 행동을 구분한 설명 예시와 확인 질문 |
| (렛유인에듀) 한국공학대학교 신소재_에너지공학 | 공정·품질·생산·설비 직무별 요구 역량 | 데이터 분석 증거를 소재 전문성·장비 운용 경험으로 확대하지 않음 |

교재 원문과 슬라이드는 저장소에 올리지 않는다. 교재의 기업 사례, 가상 지원자 경험,
공정 개선 수치는 FabGuard의 경험이나 성과로 사용하지 않는다.

## 직무별로 확인할 증거

기술 적용 후속: [개별 측정값의 통계적 이탈 검사](SPC_SCREENING.md)는 CSV 입력,
기준 구간 고정, 이후 이탈·결측 판정을 실행하는 별도 기능이다. 기존 V1 성능과 구분한다.

다음 표는 채용 적합성 판정이 아니라 프로젝트를 검토하는 안내다.
실제 지원 시 해당 채용공고의 업무·요구 역량과 대조해야 한다.

| 관점 | 설명할 문제와 행동 | 확인할 기존 증거 | 아직 입증하지 못한 부분 |
|---|---|---|---|
| 공정·생산기술 | 모든 기록을 동시에 점검하기 어려운 상황을 가정하고 점검 예산별 순위와 누락을 비교 | [실험계약](validation/EXPERIMENT_CONTRACT.md), [Top-K 결과](../results/v1/top_k_test.csv) | 공정 레시피 최적화, 익명 변수의 물리적 원인, 양산 수율 개선 |
| 품질·검사 | 포착 수뿐 아니라 놓친 불량과 정상 점검 부담, 결과의 불확실성을 공개 | [결과 요약](../results/v1/RESULTS_SUMMARY.md), [추가 검증](PHASE1_ADVANCED_VALIDATION.md), [노출 기록](TEST_EXPOSURE.md) | 불량 원인 분석 완료, 신뢰성 인증, 고객 품질 문제 해결 실적 |
| 스마트제조·데이터 | 서로 다른 출처의 데이터 역할·형식·시간·단위를 구분하고 연결 검증 근거를 남김 | [출처별 증거](../results/README.md), [외부 자료 자격 기준](EXTERNAL_DATA_QUALIFICATION.md) | PLC 제어, 실물 설비 운용, 반도체 모델의 태양광·소재 분야 전이 성능 |
| 생산기획·기술경영 | 제한된 점검 여력에서 얻는 포착과 남는 누락을 함께 설명하고 도입 판단에 필요한 정보를 명시 | [연구질문](../RESEARCH_QUESTION.md), [현장 검증 조건](CAUSAL_FIELD_VALIDATION.md) | 실측 점검 시간, 비용 절감, ROI, 조직 운영 성과 |

특히 신소재·에너지 직무에 소개할 때, 태양광 자료를 연결했다는 사실만으로 소재 특성 분석,
배터리 공정 전문성 또는 에너지 설비 운전 능력을 주장하지 않는다.

## 지원서·면접용 설명 예시

아래는 저장소에 근거한 프로젝트 설명 초안이다. 사용자의 개인 경험 진술로 제출하기 전에
본인의 실제 결정·검토 범위와 일치하는지 확인해야 한다.

- **상황(S)**: 공개 반도체 생산 데이터에서 불량 기록이 적고, 점검 가능한 범위가 제한된 상황을 가정했다. 실제 사업장의 요청을 받은 경험은 아니다.
- **과제(T)**: 자동 불량 판정 대신 먼저 확인할 기록의 순서를 제안하고, 그 순서가 무엇을 포착하고 놓치는지 보여주는 포트폴리오를 구성했다.
- **행동(A)**: [기여 기록](governance/CONTRIBUTIONS.md)에 따라 사람은 문제·범위·주장 경계를 결정하고 결과를 검토한다. Codex가 실험·평가 코드와 화면·문서·테스트의 대부분을 작성했다. 프로젝트는 고정 임계값에서 포착하지 못한 결과와 홀드아웃 노출을 공개하고, 점검 범위별 포착·누락을 함께 제시한다. 이를 모두 직접 코딩하거나 개별 오류를 직접 발견한 경험으로 바꾸어 쓰지 않는다.
- **결과(R)**: 기존 V1의 잠정 평가에서 392건 중 상위 40건에 불량 5건이 포함됐다. 전체 불량 24건 중 19건은 범위 밖이고, 점검 대상 중 정상은 35건이다. [원자료](../results/v1/top_k_test.csv)와 [잠정 판정 이유](TEST_EXPOSURE.md)를 함께 제시한다. 실제 수율·비용 개선이나 외부 전문가의 긍정적 평가는 확인되지 않았다.

‘분석력’ 같은 역량 이름보다 왜 이 범위를 선택했고 어떤 근거로 설명하는지에 집중한다.
수행 기간, 본인의 구체적 판단 사례, 현장 담당자 피드백은 확인된 기록이 있을 때만 추가한다.

### AI로 초안을 작성할 때의 입력 규칙

1. 지원공고 원문과 위 표에서 관련 있는 증거를 입력한다. 공고가 없으면 특정 기업의 요구사항을 추측하지 않는다.
2. 주장마다 근거 파일과 사람/AI의 기여 주체를 붙인다. 근거가 없으면 ‘확인 필요’로 남긴다.
3. 누락된 개인 행동은 사용자에게 질문한다. 강의 예시나 일반적인 엔지니어 업무로 빈칸을 채우지 않는다.
4. 결과 수치·분모·잠정 상태를 원자료와 대조한다. 직무별로 설명을 바꾸더라도 평가 결과와 한계는 유지한다.

### 본인이 설명해 볼 질문

- 왜 상위 점검 범위 밖의 불량도 함께 공개했는가?
- 본인이 결정한 한 가지는 무엇이며, 어떤 기록으로 확인할 수 있는가?
- AI가 작성한 코드 중 어떤 입력·출력·검증 조건을 직접 설명할 수 있는가?
- 실제 현장에 적용하려면 누가 어떤 데이터와 판단 기준을 추가로 제공해야 하는가?

이 질문에 답한 기록은 아직 이 변경에 포함하지 않았다. 설명 연습의 완료나 직무 역량의
독립적인 검증을 문서가 대신 증명하지 않는다.

## 독자가 확인할 질문

1. 왜 자동 불량 판정이 아닌 점검 순위 문제인가?
2. 5건을 찾았다는 결과 옆에 19건을 놓쳤다는 사실을 왜 제시하는가?
3. 가상 체험과 실제 데이터 평가의 증명 범위는 어떻게 다른가?
4. 작성자의 결정과 AI가 구현한 부분을 어떤 기록에서 확인할 수 있는가?
5. 현장 적용을 주장하려면 어떤 독립 데이터와 운영 기록이 더 필요한가?

이 문서는 채용 효과나 실력 향상 수치를 주장하지 않는다. 실제 사용자 검수와
직무 면접에서의 설명 능력은 별도로 확인해야 한다.
