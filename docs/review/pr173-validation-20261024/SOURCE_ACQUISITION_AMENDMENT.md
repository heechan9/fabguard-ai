# 원본 취득 방식의 실행 전 추가 기록

작성 시점: 실제 신호 디코딩·RMS·경보 계산 전, 압축 파일 구조만 확인한 상태.
기존 config SHA `55794547c6d4355a6f407a049bf973abd4e0a34d01a0c1e208477f4d34aef1ce`와 그룹 선택은 변경하지 않는다.

공식 Zenodo 서버의 HTTP 206/Content-Range 응답으로 7z 헤더를 읽었다.
아카이브는 test 약 2.515GB, train 약 1.030GB의 두 solid 압축 블록이다.
전체 다운로드가 느려, 공식 URL의 train 블록과 헤더만 병렬 range로 취득하는 방식을 시도한다.
Test 블록은 취득/디코딩/평가하지 않는다. 비대상 블록은 희소 파일의 빈 공간으로 남긴다.
따라서 이 파일은 완전한 아카이브가 아니고 기존 전체 MD5/SHA-256과 대조할 수 없다.

실행 조건: 모든 요청의 Content-Range·수신 크기 확인, 7z header CRC 통과,
사전 선택한 train 가속도 파일 20개의 멤버명·비압축 크기·CRC32 대조,
파일별 SHA-256 매니페스트를 디코딩 전에 고정한다.
그 뒤 `run_protocol_from_bytes(..., decoder='parquet')`로 동일 바이트를 디코딩한다.
추출/무결성/보정이 실패하면 실패 그대로 기록하고 설정·그룹·grid를 바꾸지 않는다.

이 방식은 선택 멤버의 압축 해제 무결성을 검사하지만 완전한 원본 아카이브 해시 검증과
동등하지 않다. CRC32는 암호학적 진위 인증이 아니며 HTTPS 원출처와 디코더를 신뢰한다.
새 결과는 기존 개발 데이터의 탐색 경보 활동으로만 보고하고,
전체 원본 독립 재현이나 이상 탐지 성능 검증이라고 부르지 않는다.
