# FabGuard 직무 연계와 인터뷰 가이드

이 문서는 FabGuard의 구현 증거를 반도체 제조 직무의 업무 언어로 설명하기 위한 포트폴리오 보조자료다. 채용공고와 직무교육 자료는 설명 구조를 설계하는 참고자료이며, 모델 성능이나 제조 성과의 기술적 증거가 아니다.

## 한 문장 정의

FabGuard는 공개 UCI SECOM 데이터를 누출 방지 파이프라인으로 분석하고, 불량을 자동 확정하는 대신 제한된 점검 여력 안에서 고위험 생산 건의 검토 순서를 제시하는 오프라인 의사결정 지원 프로토타입이다.

## 구현 증거와 직무 업무의 연결

| FabGuard 구현 증거 | 직무에서 보여주는 역량 | 현재 증거의 한계 |
|---|---|---|
| 원본 해시·스키마·결측·중복·불균형 감사 | 제조 데이터 품질 확인과 분석 전제 관리 | 실제 Fab 데이터 거버넌스 경험은 아님 |
| 학습 폴드 내부 전처리와 시간순 holdout | 데이터 누출 방지, 시간 변화 고려, 재현 가능한 검증 | 독립 데이터셋 확인 전 결과는 provisional |
| Dummy·L1 Logistic·Random Forest 비교 | 복잡한 모델보다 기준선과 검증 근거를 우선하는 판단 | 후보군이 제한적이며 생산 배포 성능을 뜻하지 않음 |
| 연속 위험점수와 Top-K 점검 큐 | 제한된 점검 자원의 위험 기반 우선배치 | 실제 인력·시간·비용을 측정한 운영 실험은 아님 |
| 데이터 계약과 웹 동기화 테스트 | 분석 결과와 사용자 화면 사이의 추적성·변경 안전성 | MES·FDC·검사시스템 연동은 미구현 |
| 엔지니어 최종판단과 결과 기록 목표 구조 | 공정·품질·설비 협업과 human-in-the-loop 설계 | 실제 조치·피드백 저장·승인 체계는 미구현 |
| 실패 결과와 holdout 노출 공개 | 결과 과장 방지, 한계 관리, 기술적 책임성 | 익명 변수로 공정 원인이나 수율 효과를 규명할 수 없음 |

## 직무별 적합도

### 1. 기반기술·제조 AI/DT

가장 직접적인 연결은 제조 데이터를 이용한 선제적 문제 식별, 분석 파이프라인과 검증 계약, 현업 의사결정 지원이다. FabGuard는 특정 공정 메커니즘을 연구한 프로젝트라기보다 여러 제조 데이터 소스를 받아 위험 신호를 만들 수 있는 분석·운영 계층의 프로토타입에 가깝다.

강조할 증거:

- 데이터 품질과 누출 방지
- 시간 변화에 대한 보수적 검증
- 모델 출력과 웹 표시의 데이터 계약
- 오류 시 임의 fallback 대신 명시적으로 실패하는 동작
- 자동판정이 아닌 엔지니어 검토 구조

### 2. 양산기술·공정기술

공정 운영·최적화 직무에는 이상 신호를 탐지하고 후속 점검 순서를 정하는 문제정의가 연결된다. 다만 SECOM 변수가 익명화돼 있으므로 특정 장비·레시피·공정 조건을 개선했다고 설명하지 않는다.

보완해야 할 실무 증거:

- 실제 변수 사전과 단위
- Lot·wafer·tool·chamber·recipe·공정 단계 식별자
- 장비 Source/Response 데이터와 품질 라벨의 시간 관계
- 재검사·설비점검·보류·재작업 결과
- 공정 엔지니어가 승인할 운영 기준과 rollback 절차

### 3. PKG&TEST·품질

Top-K 점검 큐, Fail 포착률, 검사 부담과 누락 위험의 비교는 검사·품질 업무와 연결할 수 있다. HBM·패키징 직무에 지원할 때는 적용 가능한 의사결정 패턴으로만 설명하고, FabGuard가 HBM·패키징 데이터로 검증됐다고 주장하지 않는다.

추가 검증이 필요한 항목:

- 패키징 공정별 추적 가능한 데이터
- TEST bin·불량 유형·재검사 결과
- 공정·소재·장비 변경 이력
- 실제 품질·수율·원가 KPI에 대한 전후 또는 대조 검증

## 직무 키워드에서 검증 증거까지

지원 공고의 표현을 그대로 나열하지 않고, FabGuard에서 실제로 수행한 행동과 저장소에서 확인 가능한 증거로 연결한다. 공고가 바뀌면 직무 키워드는 최신 JD를 기준으로 다시 선택한다.

| 직무 키워드 | FabGuard에서 수행한 행동 | 확인 가능한 증거 | 주장하지 않을 내용 |
|---|---|---|---|
| 제조 데이터 분석 | 원본 데이터의 해시·스키마·결측·중복·클래스 불균형을 감사 | `data_audit.json`, 데이터 감사 코드와 테스트 | 실제 Fab 데이터 거버넌스 운영 경험 |
| 이상위험 식별 | 사전에 정한 후보 모델을 학습 구간 반복 교차검증으로 비교 | `cv_summary.csv`, `manifest.json` | 모델이 물리적 이상 원인을 규명했다는 주장 |
| 검증 체계 설계 | 학습 폴드 내부 전처리와 시간순 holdout으로 누출을 통제 | 전처리·분할 코드, 누출 방지 테스트 | 독립 데이터에서 확정된 일반화 성능 |
| 점검 우선순위 설계 | 연속 위험점수를 5%·10%·20% 점검예산의 Top-K 큐로 변환 | `top_k_test.csv`, `priority_table.csv` | 실제 검사 인력·비용·수율 개선 |
| 결과 추적성 확보 | 정식 결과와 웹 JSON 사이의 데이터 계약 및 런타임 검증을 적용 | reporting 코드, 계약 테스트, 웹 오류 처리 | MES·FDC·APC·SPC 실연동 |
| 기술 통합·검토 | 문제·실험·주장 범위를 정하고 AI 에이전트 산출물을 검토·병합 | Git 커밋·PR·기여 기록 | 모든 코드를 프로젝트 책임자가 직접 작성했다는 주장 |

자소서에서는 직무 키워드 자체보다 **행동과 검증 증거**를 중심으로 쓰고, 면접에서는 마지막 열의 한계를 함께 설명한다.

## 자소서 경험 구성 템플릿

FabGuard 경험은 다음 여섯 요소로 구성한다. 지원 회사와 문항에 맞게 길이는 줄이되, 결과와 한계를 분리한다.

1. **상황:** 반도체 제조 데이터는 고차원·결측·중복·불균형 특성이 있고 모든 생산 건을 동일하게 추가 점검하기 어렵다.
2. **문제:** 단순 정확도나 0.5 임계값만으로는 제한된 점검 자원 안에서 어떤 생산 건을 먼저 볼지 결정하기 어렵다.
3. **행동:** 데이터 감사, 학습 폴드 내부 전처리, 반복 교차검증, 시간순 holdout, Top-K 점검예산 평가와 데이터 계약 테스트를 설계·통합했다.
4. **결과:** 시간순 holdout AP는 0.0935였고 고정 임계값은 Fail을 포착하지 못했다. 이를 숨기지 않고 상위 10%인 40건을 점검할 때 Fail 5/24건을 포착하는 우선순위 결과로 재정의했다.
5. **한계:** 결과는 provisional이며 익명 변수로 물리적 원인이나 수율·원가 효과를 증명할 수 없다. 실제 공장 시스템 연동과 현장 운영 검증도 수행하지 않았다.
6. **향후계획:** 실제 변수 사전과 Lot·wafer·tool·chamber·recipe 식별자, MES·FDC·검사 이력, 엔지니어 피드백을 연결해 독립 데이터와 현장 KPI로 검증한다.

### 문항별 압축 기준

- **직무역량:** 행동 3개와 저장소 증거를 중심으로 작성한다.
- **문제해결:** 낮은 holdout 성능을 확인한 뒤 자동판정에서 Top-K 의사결정 지원으로 문제를 재정의한 과정을 중심으로 작성한다.
- **협업·리더십:** AI 에이전트별 역할을 분리하고 결과·주장 경계를 검토해 PR로 통합한 책임을 중심으로 작성한다.
- **지원동기·입사 후 포부:** 회사의 최신 JD와 실제 제조 시스템을 먼저 확인하고, FabGuard는 적용 가능한 분석·검증 패턴의 증거로만 사용한다.

## 90초 프로젝트 설명

> 제조 현장에서는 모든 생산 건을 동일한 수준으로 추가 점검하기 어렵다는 문제에서 시작했습니다. UCI SECOM의 1,567개 생산 샘플과 590개 익명 측정변수를 감사하고, 데이터 누출을 막기 위해 모든 데이터 의존 전처리를 학습 폴드 내부에서 수행했습니다. 모델은 학습 구간의 반복 교차검증으로 선택하고 마지막 25%를 시간순 holdout으로 보존했습니다.
>
> 0.5 고정 임계값에서는 Fail을 한 건도 포착하지 못했기 때문에 자동 불량판정으로 포장하지 않았습니다. 대신 연속 위험점수를 이용해 점검예산 5%·10%·20%의 Top-K 우선순위를 평가했고, 상위 10%인 40건을 점검할 경우 Fail 5건을 포착하는 결과를 확인했습니다. 이 결과도 provisional로 관리하며 수율 개선이나 원인 규명은 주장하지 않습니다.
>
> 최종적으로 FabGuard를 AI가 조치를 결정하는 시스템이 아니라, 고위험 생산 건과 후속 점검 후보를 제시하고 공정·품질 엔지니어가 최종 판단하는 의사결정 지원 구조로 설계했습니다. 향후에는 실제 공정 식별자, 변수 사전, MES·FDC·검사 이력과 엔지니어 피드백을 연결해 현장 검증해야 합니다.

## 예상 꼬리질문

### 왜 정확도나 F1 대신 PR-AUC와 Top-K를 사용했나?

Fail 비율이 낮은 불균형 문제에서 전체 정확도는 Pass 예측에 지배될 수 있다. PR-AUC는 양성 클래스의 precision-recall 관계를 보고, Top-K는 실제 점검 가능한 수량 안에서 포착·누락·부담을 비교하기 위해 사용했다.

### 왜 Random Forest를 선택했나?

테스트 결과를 보고 선택하지 않았다. 사전에 고정한 후보군을 학습 구간의 5×5 반복 교차검증으로 비교해 평균 Average Precision이 가장 높은 후보를 선택했다. 선택 후 시간순 holdout 성능이 낮아진 사실도 그대로 공개했다.

### 중요 변수가 원인인가?

아니다. 익명 변수의 모델상 기여 또는 위험도와의 연관 신호일 뿐이다. 실제 원인 판단에는 센서·공정 매핑, 장비·레시피·변동점·4M·품질 이력과 도메인 검토가 필요하다.

### 실제 수율을 높일 수 있나?

V1은 실제 공장에 배포되지 않았고 수율·원가·가동률을 측정하지 않았다. 현재 증거는 공개 데이터에서의 모델 지표와 점검예산별 시뮬레이션에 한정된다. 현장 효과는 독립 데이터와 실제 운영기록으로 별도 검증해야 한다.

### AI 에이전트가 코드를 작성했다면 본인의 역할은 무엇인가?

프로젝트 방향, 문제 정의, 실험 범위와 주장 경계, 자료 선별, 결과 검토와 최종 통합은 프로젝트 책임자가 담당했다. Codex는 핵심 구현과 기술 문서, Claude는 UX·설명과 외부 근거 보완, Google Jules는 독립 감사·데이터 계약·런타임 검증을 수행했다. 저장소의 Git 이력과 문서에서 구현·검토·병합 역할을 분리해 기록한다.

## 지원 전 점검표

- 지원 회사의 신입·경력 JD에서 제품, 시스템, 공정과 세부 업무를 구분했는가?
- FabGuard와 직접 연결되는 업무 문장을 두 개 이상 선택했는가?
- 구현 증거와 아직 구현하지 않은 목표 구조를 구분해 말할 수 있는가?
- 왜 기반기술·양산기술·PKG&TEST 중 해당 직무를 선택했는가?
- 공정·품질·설비·데이터 조직 중 누구와 협업해야 하는지 설명할 수 있는가?
- 낮은 holdout 성능, 익명 변수, provisional 상태를 방어적으로 설명할 수 있는가?
- AI가 작성한 부분과 본인이 결정·검증한 부분을 저장소 기록으로 제시할 수 있는가?
- 직무에 필요한 반도체 공정·장비·소재 지식을 별도로 설명할 수 있는가?

## 참고 범위

산업·직무 분석과 취업 준비에 관한 비공개 교육자료에서 JD의 업무 단위 해석, 경험과 직무의 연결, 문제 중심 지원동기와 면접 꼬리질문 대비 원칙만 참고했다. 슬라이드의 표·그림·예시 문장은 재배포하지 않았으며, 교육자료를 FabGuard의 학습 데이터·모델 성능·제조 성과 근거로 사용하지 않는다.
