# FabGuard 실패 대응·책임·롤백 초안

상태: **현장 도입 전 운영 설계안**. FabGuard V1은 공개 SECOM 데이터의 오프라인 실험이며 이 문서는 실제 공장 절차가 승인되었거나 운영 중임을 뜻하지 않는다.

## 안전 원칙

1. FabGuard 출력은 점검 순서 제안이며 품질 판정이나 설비 제어 명령이 아니다.
2. 모델 장애·불확실성·데이터 계약 위반 시 기존 승인 절차로 복귀한다.
3. 자동 fallback 점수나 마지막 정상값을 실제 최신 판단처럼 표시하지 않는다.
4. 사람의 승인 없이 재검사, 보류, 폐기, recipe 변경 또는 설비 정지를 실행하지 않는다.
5. 사고 검토는 개인에게 책임을 전가하기보다 데이터·모델·UI·절차의 통제 실패를 추적한다.

## 역할과 결정권

| 역할 | 책임 | 단독으로 해서는 안 되는 결정 |
|---|---|---|
| 공정·품질 엔지니어 | 큐 검토, 실제 변수·공정 이력 대조, 후속 조치 승인 | 위험점수만으로 제품 폐기·recipe 변경 |
| 생산 운영 책임자 | 점검예산·SLA·기존 절차 복귀 승인 | 검증 없이 점검 범위 확대 |
| 데이터 담당자 | 식별자·timestamp·단위·결측·라벨 계약 관리 | 계약 위반 데이터를 임의 보정해 통과 |
| 모델 담당자 | 버전·입력 해시·성능·드리프트·한계 기록 | 현장 결과를 보고 잠긴 평가 기준 소급 변경 |
| 시스템 운영자 | 배포·접근권한·상태·로그·롤백 실행 | 모델 성능 해석 또는 품질 최종판정 |

실제 조직에서는 위 역할의 담당자와 대리 승인자를 배포 전에 실명 또는 직책으로 지정해야 한다. V1 저장소에는 실제 조직의 승인권한이 구현되어 있지 않다.

## 실패 모드와 기본 동작

| 실패 모드 | 탐지 신호 | 기본 동작 | 재개 조건 |
|---|---|---|---|
| 입력 스키마·단위·식별자 위반 | 계약 검사 실패, 결측 급증 | 해당 입력 격리, 큐 갱신 중단, 기존 절차 유지 | 데이터 담당자 확인과 재검증 |
| timestamp 지연·역전 | 허용 지연 초과, 순서 불일치 | 문제 reading 격리, 순서를 임의 수정하지 않음 | 시간원·수집 경로 확인 |
| 모델 또는 해시 불일치 | 승인서·artifact·환경 검증 실패 | scoring 중단, 이전 승인 버전도 자동 사용하지 않음 | 승인된 bundle 재배포 |
| 위험점수 생성 실패 | 비유한값·범위·shape 오류 | SYSTEM ERROR 표시, 수동 점검 절차로 복귀 | 오류 원인 제거와 smoke test 통과 |
| 큐 지연·누락 | SLA 초과, 입력 대비 출력 건수 불일치 | 최신성 경고, 오래된 큐를 최신 결과처럼 사용 금지 | end-to-end 건수·시간 검증 |
| 오경보 증가 | 확인된 정상 건 비율 상승 | 점검예산 확대 금지, 모델 검토 상태 전환 | 사전 기준 회복 또는 변경 승인 |
| 미탐 증가 | 사후 Fail 중 큐 미포함 비율 상승 | 자동조치 금지 유지, 기존 검사 강화 검토 | 원인 분석과 독립 재검증 |
| 분포 이동 | PSI·결측률·범위 변화 | 경고 및 사람 검토, 자동 재학습 금지 | 새 학습·평가 계약 승인 |
| UI·보고서 증거 불일치 | JSON 계약·출처 검사 실패 | 수치 대신 SYSTEM ERROR 표시 | canonical artifact와 재동기화 |
| 접근권한·감사로그 이상 | 미승인 접근, 로그 공백 | 영향 기능 중단·보안 담당자 통보 | 접근권한 재승인과 로그 검증 |

## 미탐 사고 처리 예시

위험점수가 낮았던 생산 건에서 실제 Fail이 확인되어도 담당 엔지니어 개인에게 모델 오류의 책임을 자동 귀속하지 않는다.

1. 해당 시점의 입력, 모델 버전·해시, 설정, 큐와 사람의 최종 판단을 보존한다.
2. 입력 누락·시간 정렬·단위·라벨 지연과 UI 표시 오류를 먼저 확인한다.
3. 모델 점수가 정상 생성됐는지와 당시 점검예산 안에서 순위가 어디였는지 재현한다.
4. 기존 절차를 생략했는지, 모델이 승인 범위를 넘어 품질판정처럼 사용됐는지 확인한다.
5. 동일 실패가 반복될 위험이 있으면 FabGuard 큐 사용을 중단하고 기존 절차로 롤백한다.
6. 재개에는 원인·교정조치·독립 검증 결과와 공정·품질·운영 책임자의 승인이 필요하다.

## 롤백 기준과 실행

다음 중 하나가 발생하면 모델 성능 수치가 좋아 보여도 운영 중단을 검토한다.

- 입력·모델·출력의 추적 가능한 버전 또는 해시를 확인할 수 없음
- 큐 지연 때문에 정해진 점검 시간 안에 사용할 수 없음
- 사전 정의한 미탐·오경보·점검부담 한계를 연속 기간 초과
- 익명 또는 미매핑 변수를 실제 공정 원인처럼 사용
- 모델 출력으로 기존 필수 검사나 사람 승인이 우회됨
- 보안·접근권한·감사로그 무결성 위반

롤백은 (1) 새 큐 발행 중지, (2) 화면에 중단 상태와 마지막 유효시간 표시, (3) 기존 승인 검사 절차 복귀, (4) 미처리 생산 건 재대조, (5) 관련 artifact와 로그 보존, (6) 재개 승인 기록의 순서로 수행한다. 이전 모델로의 자동 복귀는 승인·입력 계약이 현재도 유효하다는 보장이 없으므로 금지한다.

## 배포 전 확정해야 할 항목

- 기존 절차의 정확한 명칭과 롤백 담당자
- 미탐·오경보·지연·점검부담의 중단 임계값과 관찰 기간
- 큐 확인 SLA와 교대 시 인수인계 방식
- 감사로그 보존기간, 접근권한, 사고 통보 대상
- 재검사·보류·설비점검별 승인권자와 대리자
- 모델 변경·재학습·재배포 승인 및 독립 검증 절차

현재 저장소에는 실제 기업의 조직·비용·품질 기준이 없으므로 위 값을 임의로 채우지 않는다.
